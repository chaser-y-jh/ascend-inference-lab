# AI 计算与昇腾算子开发 · 课堂笔记

2026 年 11 月 21–22 日。读一个算子时，可以先追踪一块数据。它从哪里读出？哪个执行单元处理它？谁来等待结果？这里用向量加法解释数据搬运，再接上课堂的四块平方和与 Hello World，最后看同样的问题怎样出现在推理实验里。

## 数据怎样进出 AI Core？

以向量加法 `z = x + y` 为例。输入张量在设备的全局内存（Global Memory，GM）里。对一小段元素做加法时，可以把执行过程写成三步。

1. **搬入。** 按当前块的起点和长度，将 `x` 和 `y` 的对应切片从 GM 搬到片上缓冲区（Unified Buffer，UB）。
2. **计算。** 输入就绪后，Vector 单元逐元素相加，把这一段的结果放进输出缓冲区。Cube 单元主要承担矩阵乘加。
3. **搬出。** 把输出切片写回 `z` 在 GM 中的相应位置。缓冲区允许复用时，也要等前一个使用者结束读写。

一次完整的加法既花计算时间，也花搬运和等待时间。若下一块输入和当前块使用不同的缓冲区，且数据依赖允许，就有机会在计算当前块的同时搬入下一块。是否真正重叠，要看性能分析工具记录的时间线。[昇腾 AI Core 架构与数据通路](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_10_0008.html)

**最新听写的断点。** 讲师说到存储单元之间的关系会影响算子所需的指令。最后一句停在“到底”，听写中的 `join`、`tell` 所指待核对。上面的加法用于回顾此前已讲的搬运过程。

## 四个块怎样算出一个结果？

课堂给出一个 `4096 × 1024` 的矩阵。按行四等分，每个块处理 1024 行，执行同一段程序，把本块所有元素平方后求和。四个局部和相加，就得到整个矩阵的平方和。若要求 Frobenius 范数，还要对总和开一次平方根。这是 SPMD（单程序多数据）的一例。

课堂还比较了 SIMT（单指令多线程）。写程序时，每个线程可以根据自己的索引选取元素；执行时，硬件以线程组为单位调度指令。SPMD 描述同一份程序如何在多份数据上运行，SIMT 描述一组线程怎样执行指令，两者可以同时出现在一个内核里。

仓库里有一个可以心算的对照。四行分别为 `[-3, 0]`、`[0, -2]`、`[2, -2]` 和 `[0, 2]`。每块一行，局部和依次为 9、4、8、4，全局和是 25，范数是 5。把矩阵换成 4097 行，现有实现分成 1024、1024、1024、1025 行，用来检查尾行有没有遗漏。CPU 脚本顺序执行各块，验证覆盖范围与结果；四核加速需要设备计时。[分块实现](../cpu/check_reduction.py) · [五组验证结果](../cpu/results.json)

## Host 怎样启动核函数？

Host 是提交任务的 CPU 一侧，Device 是执行任务的 NPU 一侧。下面沿用课堂举的四块情形，教材 Hello World 主例配置为八块。

```cpp
hello_world<<<4, nullptr, stream>>>();
```

- `4` 指定这次启动的逻辑块数。设备端用 `AscendC::GetBlockIdx()` 取得自己的编号。在这个纯 Vector 示例里，四份程序分别读到 0、1、2、3。每份程序用编号和分块规则算出自己的数据范围。
- `nullptr` 对应课堂教材写法中的保留项 `l2ctrl`。开发版另有在同一位置填写动态 UB 大小的接口，复现时要对照工具链版本。[教材接口](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/80RC1alpha002/devguide/opdevg/ascendcopdevg/atlas_ascendc_10_0010.html) · [开发版接口](https://asc.gitcode.com/guide/programming_guide/language_extension/simd_builtin_keywords.html)
- `stream` 指定任务提交到哪条流。同一流中的任务按提交顺序执行。末尾的 `()` 放核函数实参，这个打印示例没有实参。

教材在 `hello_world.asc` 里用 `__global__ __vector__` 声明设备入口，并用 `AscendC::printf` 打印编号。Host 侧运行时接口使用 `acl/acl.h`，设备端使用 `kernel_operator.h`。若验证四块配置，可以检查完整输出中的四个编号是否各出现一次。打印先后可能变化。[CANN 学习中心 Hello World](https://gitcode.com/cann/cann-learning-hub/blob/master/tutorials/ascendc_operator_development/02_AscendC_basic/02.02_HelloWorld.ipynb)

放回 CANN 软件栈看，编译器负责把算子源码编译成可执行代码，运行时负责管理设备与流、提交任务，底层驱动负责与硬件交互。于是，“程序编译通过”“任务已经提交”“设备执行完毕”是三个不同的检查点。

## 从计算图到多卡推理，时间花在哪里？

**模型与计算图。** 在线性拟合里，模型形式是 `ŷ = wx + b`，最小二乘给出拟合目标，梯度下降是求解的方法之一。训练调整参数，推理使用已有参数处理新输入。框架可把一次前向计算展开为有依赖关系的操作，例如卷积 → ReLU → 最大池化。排查性能时，先在时间线上找到耗时操作，再检查它的张量形状、精度、布局和搬运路径。

**多卡与专家负载。** 课堂假设一次 MoE（混合专家模型）路由后，专家 A 收到 10 个 token，专家 B 收到 2 个。如果后续处理要等所有专家，先做完的 B 也得等 A。可以尝试把数据按块传送，让已就绪的部分先走。切得越细，通知与调度次数也越多。比较两种方案时，记录每块就绪、通信和计算的起止点，才能看出等待转移到了哪里。

**推理指标。** 面向用户的首个输出看 TTFT（提交请求到首个 token 的延迟），后续生成看 TPOT（首个之后每个输出 token 的平均耗时）。系统整体可以记录固定窗口内每秒输出的 token 数。对照两次结果前，先核对输入长度、实际输出 token 数、并发和计时起止点。

## 仓库实验能回答什么？

残差加法与 RMSNorm 连在一起时，输出缓冲区的用法会影响计时。仓库的 CPU 实验固定同一组 FP32 输入，在 `2048 × 1024` 形状下记录各方案 24 轮的中位耗时。

- 常规实现每次新建临时数组，耗时 **9.61 ms**。
- 复用缓冲区，再复制出一份可保留的独立结果，耗时 **5.57 ms**。若调用方要保存上一次输出，应选这一项与常规实现对照。
- 直接返回下一次调用会覆盖的缓冲区，耗时 **3.82 ms**。这种用法要求调用方在下次调用前用完结果。

两种复用方案都通过了 FP64 参考值检查。这组数字来自 Windows CPU 上的 NumPy 实验。课程提出的下一个问题是，在昇腾 NPU 上运行 Qwen3-8B 时，短、长输入分别能否从 RMSNorm 融合中获益。仓库已有结果分析工具，该问题仍待实机测量。[CPU 原始计时](../rmsnorm/observed.json) · [性能对照图](../rmsnorm/latency.png) · [NPU 实验设计](../inference/README.md)
